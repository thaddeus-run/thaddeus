THA-151 migrating encrypted repositories to trusted-service storage

How an owner moves a keyless repository into the trusted service that THA-150 defined: a signed consent, the original records kept as evidence, an import that resumes, a check of every version before cutover, and a way back. Built on f9ced0d.

Goal and shape

Goal. Implement the six migration rules in section 8 of the architecture contract as a library in public core.

Architecture. A new package, @thaddeus.run/migrate. The owner's client reads the source through the shipped Client, signs a consent and decrypts files on its own machine. A Migrator on the service side checks the consent and every original record, seals files through THA-150's KeyCustody, rebuilds every version before cutover and writes service head records through Authority.advance. The keyless server and the CLI do not change.

Tech stack. TypeScript on Bun, @thaddeus.run/authority, log, store, client, platform, BLAKE3 from @noble/hashes.

Global constraints
  • Only the DID that signs the source's head chains may migrate it, through its own credential.
  • No content key or identity key leaves the owner's machine.
  • No original record is re-signed or changed. Service records never pass for an actor's signature (ADR 0006).
  • The migration never writes to the keyless server, so repositories that are not migrated keep working.
  • Every stored record carries a format version, and readers refuse versions they do not know.

What the code says today

Signal Evidence
Only the owner can read everything MemoryStore.put issues one capability to the author. Delegates' content reaches the owner only because the CLI grants it, so the owner's client is the one place every file decrypts.
Plaintext ids are signed canonicalOp signs [payload.id, payload.plaintext_id], and plaintext_id is the BLAKE3 of the bytes. The service can check each file it receives against the owner's signature without any key.
Head sets only grow verifyHeadChain refuses dropped_heads, so the newest record's closure contains every earlier version's operations.
The trusted side has custody and history, not a repository format KeyCustody.seal binds content to tenant, repository and path, and Authority.advance names a revision string. Nothing defines what a revision is.

Decisions to check first

# Decision Why
1 The owner's client decrypts and sends plaintext No key ever leaves, so there is no key-upload mode to authorize or misuse.
2 Only the source owner may migrate The owner is the DID the head chains name and the only one that reads every file.
3 The consent pins every version's revision The service proves it rebuilt the history the owner saw, not just the newest tree.
4 Evidence keeps the original ciphertext and capabilities An archive restores the keyless repository with every original signature intact.
5 One service head record per source version History survives the move, and an interrupted cutover resumes by version.
6 The keyless source is never frozen Rule 6 keeps it working. Cutover refuses a source that moved instead.
7 Rollback keeps service head records They are append-only under THA-150. Hosts serve only the cutover state.
