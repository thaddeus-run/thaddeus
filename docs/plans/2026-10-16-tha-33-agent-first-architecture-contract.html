THA-33: establish the agent-first architecture and migration contract

Thaddeus is now built first for many agents working on one repository at once. This plan writes the October 16 architecture decisions into the repository and brings the manifesto, README, architecture notes, glossary and onboarding guide in line with them. It covers the public core only and changes no runtime code.

Sources: THA-33, GitHub #86, and the 16 October architecture proposal draft. This issue blocks THA-113, THA-117 and THA-150.

Outcome and scope

A reader who opens the repository should find one document that says what Thaddeus is building and in what order. Every top-level document should agree with it. That means three deliverables.

  • Two short ADRs record the two decisions that reverse earlier commitments. A trusted code-processing service replaces mandatory host-blind encryption. Hosted remote workspaces and external agents come before local-folder parity, customer hosting and first-party orchestration.
  • One contract document, docs/agent-first-architecture.md, carries the rest. It holds the product decisions, the trust model, the component responsibilities and the semantic-editing requirement. Authority over semantic editing stays with THA-113. It also holds a table of targets against measurements, the single ordered build queue, the superseded and parked work, and the migration contract for existing encrypted repositories.
  • README, ARCHITECTURE.md, CONTEXT.md, the getting-started guide, the server package README, the manifesto and CHANGELOG.md stop presenting the keyless server as a permanent promise. Each one links to the contract.

Not in scope

  • Runtime behaviour. The shipped server still holds no repository keys. The docs describe that as the current state, not the destination.
  • ThadHub implementation and its private docs.
  • Rewriting the manifesto body. It gets a dated amendment. Nobody edits 4,000 lines of essay for this.
  • Package reference READMEs other than the server one. They describe shipped behaviour accurately today.
  • The docs site and landing pages under apps/. The landing deck already says "a million agents writing code in parallel". The docs site explains the shipped permission model, which does not change.
  • Editing Linear issues. The PR body ticks THA-33's checkboxes.

Task 1: two ADRs docs

Copy the voice of docs/adr/0001-actor-attribution-is-a-declaration.md. Each ADR has a title, a paragraph of decision and consequence, and a paragraph of mechanism or boundary. The existing ADRs have no Status, Context or Decision headers, so these don't either.

Step 1: write docs/adr/0003-trusted-code-processing-service.md

Title it # A trusted service processes code.
  • Paragraph one states the decision. A Thaddeus-hosted or customer-hosted service may read repository plaintext to answer authorized requests for browsing, diffs, search, semantic queries and execution. Storage stays encrypted with service-managed keys. The trusted-service path drops the promise that the host cannot read code. Browsing, search and execution all need plaintext, so the promise never covered them anyway.
  • Paragraph two lists what stays. Read, edit, execute, review and integrate remain separate scopes with repository and path restrictions and revocation. Storage stays encrypted. Every plaintext access leaves an audit record. Untrusted execution runs isolated per tenant. ADR 0001's rule still holds: a service-recorded action is never labelled an agent signature.
  • Paragraph three names what this supersedes. That is mandatory extension key custody in THA-77 and browser decryption in THA-75. The shipped open-source server keeps its keyless behaviour until THA-150 lands the authority contract and THA-151 the migration path. Link both issues and the contract document.

Step 2: write docs/adr/0004-hosted-workspaces-and-external-agents-first.md

Title it # Hosted remote workspaces and external agents come first.
  • Paragraph one states the primary goal. Thaddeus is for large-scale parallel agent development on one repository, and the design target is 1,000 or more simultaneous agents.
  • Paragraph two gives the delivery order as a numbered list of four. First, Thaddeus-hosted remote workspaces over shared code. Second, local-folder compatibility for existing checkouts and the current CLI, which keeps working but is not the design centre. Third, customer hosting of the trusted service. Fourth, first-party orchestration, once external agents such as Claude Code and Codex can connect through the remote workspace API.
  • Paragraph three covers tracking. One ordered build queue in Linear replaces milestones, cycles and due dates. The view is called "Thaddeus build order" and sorts by title ascending. The contract document holds the repository copy of that order.

Step 1: header and "1. Product decisions"

Title it # Agent-first architecture and migration contract. Add a status line. THA-33 ratified it on 2026-10-16. It supersedes the scope of issues rewritten under the October 16 redesign. The proposal draft stays at its postplan URL.

Then write one paragraph on the goal. Parallel agent development is the primary product goal, with 1,000 or more agents on one repository.

Section 1 is a table. Use these rows and the proposal's values.

  • Core model. Isolated lightweight workspaces over shared code, with structured editing, durable checkpoints and controlled integration.
  • Hosting. Thaddeus-hosted first, customer hosting later.
  • Agents. External agents connect first. First-party orchestration comes later.
  • Local folders. Compatibility stays, but local folders are not the design centre.

  • Saving. Automatic saves in small batches, plus explicit named checkpoints.

  • Scale. 1,000 or more simultaneous agents on one repository.
  • Work tracking. One ordered Linear queue with no daily cycle.

Step 2: "2. Trust model"

Write two subsections.

Today, as shipped. Three present-tense sentences that link ARCHITECTURE.md. The open-source server holds no repository keys and verifies signed uploads. It serves a ciphertext mirror, and only the owner signs landings. Timed reveal is the known exception.

Direction, per ADR 0003. A trusted service processes plaintext for authorized requests. List the guarantees that stay, in this order.

  1. Scoped authority. Read, edit, execute, review and integrate are separate scopes. Authorization covers reads, queries, logs, caches and subscriptions.
  2. Encrypted storage with service-managed keys.
  3. Short-lived scoped credentials for agents and revocable sessions for humans.
  4. Audit records for plaintext access and for history advancement.
  5. Tenant isolation for untrusted execution. Secrets are scoped execution inputs, never source files.
  6. ADR 0001's attribution rule. Service-recorded activity is never an agent signature.

Close with the two rejected alternatives, one sentence each, and why each lost. Encrypted storage with separately trusted compute made key distribution too complex. A host that cannot decrypt rules out browsing, search and execution.

Step 3: "3. Components and responsibilities"

A table of five components, each with one sentence on what it is responsible for. They are workspaces and storage, the semantic engine, the integration service, isolated execution workers, and the durable repository store.

Below the table, state the boundary rule. These are lines of responsibility, and they need not be separate deployments. The document makes no multi-node correctness claim while durable state lives in process memory.

Then four short paragraphs.

  • Workspaces. A workspace points at an immutable base revision and stores only what changed. Each save carries a retry identifier and a sequence number. The service acknowledges a save only after it is durably committed. Named checkpoints bind exact content to exact operation versions. Base updates happen only at explicit safe boundaries. Shared workspaces need version-checked writes, so the last writer never silently wins.
  • Execution. Workers attach on demand. Concurrency has its own limit, separate from workspace count. Suspension keeps files and environment definitions. Resuming the exact process is deferred.
  • Integration. Integration agents work in isolated workspaces under path authority, compute budgets and a cap on attempts. Each candidate is tested at an exact revision, and the shared head advances atomically. Independent repositories never wait on a shared landing lock.
  • Development interface. List the five minimal authenticated ThadHub views from the proposal and mark them as private product work.

Step 4: "4. Semantic editing is an early delivery requirement"

Structured editing means rename, function edits and symbol-scoped authority. It ships in the first useful release. It is not a later layer, because agents need edits that a stale view of the code cannot invalidate.

Describe the proposed shape. Mark every sentence as proposed.

  • Immutable file content plus a versioned change journal is the source of truth.
  • The symbol graph is a projection the system can rebuild, tied to revisions.
  • File edits and structured edits go through one transaction path.
  • A stale graph cannot authorize a destructive edit.
  • TypeScript and JavaScript are the proposed first language family.

Then put the deferral in its own paragraph. THA-113 decides whether the graph or the journal is authoritative. It also decides how comments, formatting, unsupported syntax and external edits survive without loss, how symbols keep stable identity, what preconditions guard a stale index, and how rollback works. This document does not pre-empt any of it. Link docs/specs/2026-07-07-thaddeus-pillar-08-semantic-graph-design.md as prior art that THA-113 has to reconcile.
