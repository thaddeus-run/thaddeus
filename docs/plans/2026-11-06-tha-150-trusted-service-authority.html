THA-150 trusted-service authority plan

How the trusted service decides whether a browser, an external agent or an integration worker may read, edit, execute, review or integrate, right now. Built on branch feature/tha-150-007-core-trusted-service-authority-and-scoped-agent-sessions, first commit bf6396b. The contract itself lives in docs/superpowers/specs/2026-11-06-tha-150-trusted-service-authority-design.md.

Goal and shape

Goal: a public-core authorization contract with a reference implementation that meets the four THA-150 acceptance criteria, with no server routes yet.

Architecture: one new package, @thaddeus.run/authority. An Authority keeps each tenant's versioned policy in a Backend, issues holder-bound credentials, and checks every use against the credential's grants and the policy of that moment. KeyCustody holds per-repository data keys wrapped by a root key provider and is the only way plaintext moves. Shared history advances into service-signed records that keep who asked apart from who signed.

Tech stack: TypeScript on Bun, @thaddeus.run/identity for Ed25519 did:key signatures, libsodium XChaCha20-Poly1305 for wrapping and content, the existing durable nonce store and putIfAbsent from @thaddeus.run/store and @thaddeus.run/persist.

Global constraints
  • Public core only. ThadHub sign-in, routes and a KMS provider are other issues.
  • The shipped server stays keyless and unchanged.
  • Single node, like the shipped server. Cross-node revocation is THA-83.
  • A service record is never presented as an agent signature (ADR 0001, ADR 0003).

Decisions taken without a grill round

The issue ran under full send, so nobody answered planning questions. These are the calls to review first.

# Decision Why
1 One new package and no server routes THA-152, THA-148, THA-89 and THA-67 own the routes and are blocked on this contract.
2 Every credential is bound to a holder key, browsers included A stolen token alone does nothing, and replay protection is the same for every caller. Browsers hold a non-extractable Ed25519 WebCrypto key.
3 Effective authority is credential grants intersected with the current policy Narrowing a policy narrows live credentials at the next check, with no revocation step.
4 A member may issue agent sessions to other keys from its own grants 1,000 agents should not need 1,000 policy edits. Revoking the member revokes them.
5 Lifetimes: agents and workers 15 min default, 1 h ceiling; humans 8 h default, 12 h ceiling Short-lived for agents, a working day for humans. Hosts may lower, never raise.
6 The service records advancements and journal entries; actor signatures are optional claims ADR 0006. Settles the question the semantic authority design left to THA-150.
7 Queued work re-checks at redemption and redeems once Work never runs on authority that expired or was revoked while it waited.
8 One data key per repository, wrapped by a root key provider Simplest key layout that keeps tenants and repositories apart. Rotation is later work.

Task 1: Scopes, paths and signed tokens

Create packages/authority/src/scope.ts · src/codec.ts · src/token.ts · src/proof.ts · src/errors.ts · package scaffolding

Consumes
Identity, PublicIdentity from @thaddeus.run/identity.
Produces
Scope, Grant, patternCovers, grantsCover, grantsSubsume; encodeCredential / decodeCredential (thc1. tokens); proveAction, proveIssue, proveRevoke; AuthorityError with stable codes.
  1. Validate patterns **, dir/** or an exact relative path; refuse ., .., empty segments, backslashes and control characters.
  2. Sign the exact payload text tokens sign domain + "\n" + base64url(JSON), so verification never re-serializes JSON.
  3. Bind proofs to one token and one action the holder signs a digest of the token, the canonical action, a timestamp and a nonce.
