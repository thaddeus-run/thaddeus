Authorization decisions

  1. Add an owner-signed ReviewerCapability in @thaddeus.run/review, with its own signing domain. Fields: repository, reviewer DID, issuer DID, nonempty path scopes, issuance time, unique grant nonce, and finite veto limits. Derive the grant ID from canonical signed content. Validate at registration and replay; freeze verified authority data. A write Delegation cannot decode or verify as a reviewer capability. Review authority grants no code upload, land, grant-management, or decryption authority.
  2. The repository owner remains an explicit full-scope reviewer. Other identities require a reviewer grant even when they also hold a write delegation. Review scopes govern vetoes; write scopes govern writes. Do not intersect the two: a deliberately granted src/** reviewer with a docs/** write delegation must be able to review src/** without gaining authority to write there. This replaces THA-24's interim wording about checking the write delegation with the separate reviewer capability requested by both issues.
  3. New scoped veto records use a versioned signing domain covering repository, grant ID, target op ID, reviewer, reason, and timestamp. Owner records use an explicit owner authority marker. Retain v1 decoding and signature validation. Bind each external review to its exact grant so revocation followed by a new grant never resurrects old vetoes or accepts a veto made for another repo.
  4. Require the request signer to equal the veto reviewer; do not permit relaying another person's veto in this slice. Verify the record, current grant, repo, and an existing signature-valid target op in that repo before persistence. Check the target's stored path against the review grant, never a caller's claimed path. Use the existing exact-path / prefix/** / ** semantics and reject traversal or ambiguous path spellings. Reject unknown targets; callers can submit again once the op exists. Same-bundle targets must have been successfully ingested before a writer's veto is evaluated.
  5. At land time, re-evaluate authorization, exact grant revocation, target scope, and withdrawal under the same repository lock as head advancement. An explicit DID allowlist alone is insufficient: it cannot express per-op scope or distinguish a revoked grant from a later grant to the same DID.
  6. Keep write and review revocation independent. An owner-signed revocation terminally disables one reviewer grant and all vetoes made under it, while retaining history. A fresh grant has a fresh ID. Allow reviewer-signed withdrawal of their exact veto, and owner-signed dismissal, both append-only and bound to the veto's stable content ID. Replaying the same veto cannot undo withdrawal. A new veto after withdrawal is a new, rate-limited record.

Implementation sequence within the PR

1. Review records, registry, and durable lifecycle

  • Add capability, grant revocation, scoped veto, withdrawal/dismissal records, canonical signing helpers, and a review registry without importing the agent package. Export through packages/review/src/index.ts.
  • Extend the review log to retain immutable audit history and compute whether a veto is active, revoked, withdrawn, unauthorized, or legacy. Keep cryptographic validity distinct: a valid signature does not imply current authorization.
  • Persist signed records and server receipt time before changing in-memory projections. Use one durable acceptance envelope for the veto and receipt timestamp, so a crash cannot persist a veto without its rate accounting.
  • Reload grants, revocations, vetoes, and withdrawals deterministically. Invalid authority records confer no rights; unreadable revocation state must fail closed rather than silently re-enable a grant. Invalidate review caches on repository deletion and failed mutations, following existing server patterns.

2. Owner management and reviewer submission endpoints

  • Add owner-authenticated grant/revoke endpoints under /repos/:name/reviewers, plus a bounded, paginated grant listing. Verify both request and record signer against repository ownership, and bind records to the requested repository.
  • Add signed POST /repos/:name/vetoes and a signed withdrawal endpoint. Accept only their review payloads; a reviewer cannot smuggle objects, ops, store capabilities, provenance, semantic ops, pending reveals, or head updates.
  • Add a paginated veto-history read endpoint. Follow the repository's current read-access model and make actor, authority ID, target, reason, receipt time, signature validity, and lifecycle status inspectable. This is history, not a pending-review queue or an approval concept.
  • Thread authenticated submission context into ingestBundle; route general push and owner revoke/recall veto entries through the same validator. General push remains owner/write-delegate only. A writer without review authority can still upload code, but its veto entries are rejected with no veto side effects.
  • Preserve existing per-item accepted/rejected semantics for bundle ingestion. Use stable rejection codes for missing authority, signer mismatch, wrong repo, unknown target, invalid signature, scope, revoked grant, and rate exhaustion.

3. Land policy and upgrade behavior

  • Make blockOnVeto require an explicit reviewer allowlist, and add a predicate or policy context for per-veto authorization/lifecycle checks. Update every internal caller, tests, examples, and documentation. Remove implicit trust of every DID; define an empty allowlist as trusting nobody. The server normally passes at least the owner.
  • Compose owner plus active reviewer grants with the existing policy floor; a veto from an authorized reviewer still overrides otherwise green gates.
  • Existing owner v1 vetoes remain effective if their target is valid in the repo. Existing non-owner v1 vetoes remain visible as legacy audit entries but stop blocking, because they lack an authorization-bound grant ID. Require a new grant and fresh scoped submission to make them active. Never auto-promote write delegates to reviewers or reinterpret old vetoes when granting review rights.
  • Document this security-related behavior change and the explicit-allowlist API change in package docs and CHANGELOG. Preserve original signed bytes.

4. Abuse limits and concurrency

  • Proposed configurable server ceilings: 60 newly accepted vetoes per reviewer per repo per trailing hour, 256 active vetoes per reviewer per repo, and 256 veto entries per request. Capability limits may tighten these ceilings. Apply server ceilings to owner submissions too. Validate finite safe integer limits; retain existing request-body and decoded-field byte limits.
  • Charge only distinct accepted records, using trusted server receipt time. Identical retries do not duplicate history or consume budget; check current authority before reporting success. New grant IDs do not reset DID-level rate/active limits. Active limits aggregate across that reviewer's grants.
  • Rebuild recent usage from durable acceptance records after restart; prune expired in-memory window entries without deleting audit history. Keep a bounded index for active vetoes and current rate usage.
  • Serialize check, persistence, and projection with withRepoLock, and update repository revisions for cursor consistency. Test both orderings of submit/revoke and submit/land. A veto accepted after a land does not undo it.
  • Revocation and withdrawal must remain possible when submission budgets are exhausted. Existing repository/object quotas do not bound all review metadata; do not claim they do. This slice bounds submission rate and active veto count, not lifetime audit storage; broader retention policy remains separate.

5. Client and CLI integration

  • Add review grant/list/revoke and veto-history/withdraw methods to the client; update DTO/protocol exports, pagination handling, and browser-safe imports.
  • Route pushVetoes to the dedicated endpoint while preserving its result contract. Update CLI veto to select the active grant and sign the scoped record; owner usage remains straightforward. If multiple grants cover an op, select deterministically and permit explicit grant selection.
  • Add minimal CLI reviewer grant/list/revoke and veto withdrawal commands using the existing local identity and signed-request plumbing. Update vetoes and log so a signature-valid but inactive veto is not displayed as blocking.
  • Pull/clone must retain the signed authority and lifecycle records needed to interpret veto history offline. Use the bounded DTO/pagination conventions; imported records do not bypass server submission checks or automatically acquire authority on another server/repo. A local history view may be stale until refreshed and must not be presented as an authoritative land decision.

Acceptance tests

  • Reproduce THA-24: a docs/** write delegate uploads a valid veto for the owner's unlanded src/** op. Reject it; owner land succeeds before and after delegate revocation and server restart.
  • An outside reviewer with only a src/** review grant can veto matching code; cannot upload code, land, issue grants, or veto docs/**. Verify negative cases with signed valid payloads so failures demonstrate authorization, not parsing.
  • A holder of both roles uses each capability independently, including review scope wider than write scope. Revoking either role leaves the other intact.
  • Forged/foreign-owner grants, wrong repo, wrong grant ID, signer substitution, invalid or unknown targets, traversal paths, and mixed-payload smuggling fail.
  • General push and owner recall cannot bypass reviewer checks; owner cannot launder another DID's veto. Successful code items preserve bundle semantics.
  • Authorized veto blocks a green land without advancing the head. Revocation, withdrawal, and dismissal remove its effect without deleting audit evidence. Exact replays and fresh grants do not resurrect disabled records.
  • Seed pre-upgrade data directly: owner v1 veto remains effective, outsider v1 veto cannot block, and granting review rights never activates old data.
  • Rate boundary, batch limit, active limit, duplicate retries, fake signed timestamps, restart, new-grant attempts to reset limits, concurrent submissions, and storage failures preserve budgets and durable state.
  • Race tests establish serialized outcomes for revoke/submit and submit/land; unreadable revocation storage cannot silently authorize old grants.
  • Client/CLI outside-reviewer flow, paginated audit history, clone/pull lifecycle synchronization, and browser import smoke tests cover the public surfaces.

Implementation record

Final checks passed: 384 tests across review, platform, server, client, and CLI. All five affected package typechecks passed, as did the platform example typecheck and demo. moon run root:format root:lint passed with 45 existing warnings and zero errors. git diff --check passed.

The feature is implemented on feature/tha-6-tha-24-scoped-reviewer-veto. No commit, push, or PR has been created.

Review grants and signed vetoes are repository-bound. Every server veto ingestion path uses the same validator. Revocation and withdrawal retain signed history. Recent receipt indexes are pruned after durable acceptance; backward server clocks fail closed for new submissions.

Observed live run: the compiled server retained a veto across restart over FileBackend. The CLI dispatcher sent real HTTP requests using isolated identities. Land returned exit 1 before and after restart; withdrawal returned exit 0; land and a second owner upload then returned exit 0. The revoked reviewer could no longer submit. The compiled binary also printed reviewer command help.

The domain and whole-change reviews found replay, accounting, and error-mapping defects. Each was corrected and covered by a regression. Automated checks cover both successful quota rollback and recovery when publishing rollback also fails. Approval-required policy and the review queue remain in THA-97 and THA-98. Offline status can lag the server, and lifetime audit retention is not bounded by the submission limits.
