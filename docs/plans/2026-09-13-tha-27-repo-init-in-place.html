THA-27: Initialize a repository in place

Implementation plan, September 13, 2026. Based on main at 8451f4c.

Goal: thaddeus init <name> adopts the current directory, preserves its files, and leaves included files ready for the first push.

Architecture: Move identity setup to thaddeus identity init [--force]. Repository initialization requires an existing identity and coordinates signed remote creation and verified clone APIs. Stage only Thaddeus metadata, publish the working-copy config last, and retain a recovery record when a remote create may have succeeded. Existing files remain uncommitted.

Tech stack: TypeScript, Bun, the existing Client and FileBackend packages, Node filesystem APIs, and moon tasks. No new dependencies or server protocol changes.

Spec: THA-27, supplied issue description reproduced below. Supporting source: docs/plans/2026-07-12-thaddeus-analysis-roadmap-thadhub.html, section 3 and product/collaboration P13.

Implement the tasks in order. Checkboxes track implementation progress. Do not commit or push without a user request.

Scope and acceptance criteria

  • thaddeus init <name> adopts the current directory without moving its files.
  • Existing files become the initial working-copy state with explicit ignore behavior.
  • Identity/repository collisions, nested roots, empty directories, and rollback on failure are handled.
  • The real first-run path is exercised end to end and documented.

Offline checkpointing belongs to THA-96. This command requires an explicitly selected server and creates its empty signed repository. It does not commit, upload file contents, or land changes. The documentation edit overlaps only the getting-started section needed here; version cleanup and the agent demo remain THA-29.

Global constraints: use Bun and moon; preserve trailing newlines; no dependency version changes; no default hosted server; no unrequested refactors. Work on feature/tha-27-dx-thaddeus-init-that-adopts-the-current-directory-repo-init. Keep this as one coherent feature change.

Empty directories and non-regular entries Empty root succeeds with empty main and clean status. Empty subdirectories stay on disk but are not tracked. Preserve symlinks and special files without following or tracking them, and report the skipped count.
Roots and metadata collisions Canonicalize cwd through realpathSync. Reject initialization inside another working copy and around descendant working copies. Remote name collision A fresh attempt receiving 409 fails even if the owner is the same. Never implicitly adopt an unrelated remote or delete it. Recovery is allowed only for a matching prior local attempt.
Identity collision Reject corrupt JSON, invalid seed length/encoding, or a stored DID inconsistent with the seed. Do not silently rotate or overwrite. In identity init only, use exclusive creation for the non-force path; on EEXIST load and validate the winner.

Rollback and recovery boundary

A filesystem update and an HTTP request cannot commit atomically. The plan guarantees rollback of invocation-owned working-copy files on a caught failure before config publication. It preserves user files. The pre-existing identity remains untouched, and a possibly created remote remains recoverable. This is a deliberate part of the proposed contract, not a claim that all effects disappear.

Phase Failure and retry behavior
Preflight Read and validate arguments, the required existing identity, roots, and ignore inputs without mutation. Failure leaves all state unchanged.
Prepare local state Load the existing identity without writing it and reserve a per-root init lock. Create a unique stage beneath .thaddeus; prepare ignore bytes and config there. Save a mode-0600 journal under ~/.config/thaddeus/init/, keyed by SHA-256 of canonical root. Record only paths, DID, repo, server, phase, and ownership evidence, never private seed bytes.
Before create request Persist phase create-attempted before sending POST. A definite rejected request removes the journal. A transport failure or 5xx keeps it because the server may have persisted the repository.
Create acknowledged Persist remote-created. Call Client.clone into the stage with expectedOwner: identity.did. Require version-zero empty main and zero operations. Do not call materializeToDisk.
Publish local state Recheck root and ignore inputs. Install a seeded ignore file exclusively, move staged store into the reserved store path, and publish config last through an atomic no-replace operation. The config is the commit point. Record ownership before each filesystem action so a crash between action and journal update is recoverable.
Caught failure before commit point Remove only stage/store/ignore entries created by this attempt, and only if their recorded inode and relevant bytes still match. Retain changed or unfamiliar entries and report their paths. Remove an invocation-created metadata directory only if empty. Never alter the identity. Keep the journal if remote creation succeeded or is uncertain; report the server, repo and exact retry command.
Retry after uncertain remote outcome Require journal root/server/repo/DID to match, and verify no active init holds the lock. Try verified SDK clone. If remote is definitively 404, repeat create. If it is owned by this identity and still version-zero empty main, finish adoption. A changed head, owner mismatch, malformed response, or ambiguous error preserves the record and exits 1. No automatic delete or materialization.
Crash and post-commit cleanup A matching config and valid store prove local commit even if the journal remains. A rerun finishes cleanup and returns success. Cleanup failure after commit prints a warning and returns success with initialized state. After a crash before commit, inspect the journal and ownership evidence before removing artifacts or resuming. Never recursively clear an unknown metadata directory.

Use an exclusive .thaddeus/init.lock directory with attempt ID and PID. A live or uninspectable PID blocks another init. Recover a stale lock only when the recorded local process is confirmed absent and the journal matches. PID reuse can require manual lock inspection; it must not cause automatic lock stealing. This does not add concurrent access support to the existing single-process object store.

Automatic remote deletion is excluded because the current delete API could erase work another process added. Recovery may refuse a now-populated remote; the diagnostic directs the user to clone it into a separate directory and reconcile their files. Full remote transaction rollback would require a separate protocol change.
